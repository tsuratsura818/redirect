# CLAUDE.md — Pivolink まわりみち（京都モデル）

## 1. プロジェクト概要

動的QR周遊サービス「まわりみち」。参加者は最終目的地（清水寺など）を自分で選び、
そこまでの道中をエンジンが「回廊内の寄り道スポット」二択で誘導する。
QRコードは物理的に固定のまま、遷移先だけをサーバー側で制御する。

## 1-0. ★このプロジェクトの起点（最重要・ここを外すと全部ズレる）

**起点は「PivoLinkで何ができるか」を見せること。** まわりみちの事業展開も必須だが、
きっかけは PivoLink の活用アイデアを広げ、登録ユーザーを増やすことにある。

したがって **「PivoLinkを使って作った」では足りない。PivoLinkの機能が実際に動かしている**必要がある。

- 「毎回行き先が変わる」を作っているのは **PivoLink の `redirect_rules`**（`ab_test` / `time_of_day` / `scan_step`）。
  まわりみちアプリが自前で時刻を見て分岐する実装に**戻してはいけない**
- サイト・管理画面は企画用のオリジナルでよい。**基盤の判断がPivoLinkにあること**が要件
- 受け口は `src/lib/pivolink.ts` の1ファイルだけ。ここを迂回する分岐を書かない
- 証明: `npm run e2e:pivolink -- <url>`。**PivoLinkのルールを止めると体験が実際に変わる**ところまで担保する
- 詳細と役割分担 → `docs/pivolink-integration.md`

**PivoLinkが担当している範囲**（アプリ側に実装を戻さない）

| 機能 | PivoLinkの何 | 作成スクリプト（pivolink直下） |
|---|---|---|
| 毎回違う行き先 | `ab_test` | `_create-mawarimichi-rules.mjs` |
| 時間帯で変える／閉店中の振り替え | `time_of_day` | 同上 |
| 2回目・3回目は別の道 | `scan_step` | 同上 |
| 実験の開始前・終了後 | `schedule` / `scheduled_switch` | `_create-mawarimichi-campaign.mjs` |
| スポンサーCM（文言・秒数・クーポン） | クッションページ | 同上 |
| CMのスポンサー振り分け・表示回数計測 | `ab_test` / `scan_logs` | 同上 |

**まわりみちのオリジナル機能はこの3つだけ**（ステートレスなリダイレクトでは原理的に持てない）:
回廊の絞り込み ／ スタンプ・スタンプ帳 ／ 混雑の自動連動

**★Server Action をまたぐ画面では PivoLink の判断を hidden(`pv`) で持ち回る。**
忘れると目的地を選んだ瞬間に band/pick が消え、開示もA/Bも効かなくなる（実際に作り込んだ）。

### 第三者提供の前提（2026-08-18 追加・設計要件）

**「PivoLink とまわりみちを渡せば動く」「スクリプトを一度も叩かずに両方のUIだけで運用できる」**
が要件。AIや手作業スクリプトで裏から整える前提の機能を残さない。

| やること | どの画面 |
|---|---|
| セットアップ確認・初回SQL | `/admin/setup` |
| キャンペーン設定・開催期間・スタートQR・CM枠 | `/admin/campaign` |
| 目的地の追加・編集 | `/admin/goals` |
| スポットの追加・編集（保存でPivoLinkに自動反映） | `/admin/spots/*` |
| **見出し・タグライン・ナビの名前と台詞・画像・朱印・OG画像** | `/admin/campaign` の「見た目と語り口」 |
| ルールの微調整・アナリティクス | PivoLink のダッシュボード |

**★文言をコードに直書きしない。** 街やキャラクターで書き換わるものは `campaigns.hero` /
`campaigns.navigator`（JSONB）に置き、`lib/branding.ts` が既定に重ねる。空欄なら既定に落ちるので、
既存キャンペーンは何もしなくても動く。ボタンや単位のような「動きが変わらない語」は
コード側（`lib/i18n.tsx`）のままでよい — 全部をDBに出すと翻訳の抜けが即バグになる。

**新機能を足すときは「その操作はどちらかのUIからできるか」を必ず確認する。**
`_create-mawarimichi-*.mjs` は残してあるが**復旧用のフォールバック**であって、
運用手順に載せてはいけない（載せた時点で第三者に渡せなくなる）。

**★QR画像は必ず PivoLink の `/r/` を焼く。** アプリの直URL（`/s/<token>`）を刷ると、
時間帯・A/Bテスト・開催期間・CMが全部素通りになり、しかも後から遷移先を変えられない（＝刷り直し）。

- 事業目的: オーバーツーリズムの需要分散。観光庁「面的受入環境整備促進事業」（補助率2/3）の対象領域
- 体験の核: **目的地の自由 × 道のりの偶然**。「連れ回された」ではなく「良い旅だった」を残す
- 収益: 自治体/DMO導入費 + 月額運用 + スポンサーCM枠（第3の財源）
- KPI: 分散率 / まわりみち率（歩行距離÷最短距離、実測中央値163〜241%。飲食スポット5件を足して13件になり、
  寄り道の間隔が詰まったぶん下がった）/ クーポン利用率 / ナビ利用率
- **実運用時間は 9:00〜16:00**。17時以降は開いているスポットが13件中2〜3件しかなく、5つの寄り道が成立しない。
  告知・チラシにこの時間を書くこと（→ `docs/hours-guide.md`）
- ナビゲーターは**「ルル」**（キャラクターコラボ枠・和服）。素材は `public/navi/`。
  差し替えできるよう参照は `NaviFace` / `NaviStanding`（`components/graphics.tsx`）経由に限る

**UI/UXの正は `mockup/pivolink-kyoto-spot-mockup.html`。** 画面構成・文言・挙動はこれに従う。
迷ったらモックアップを開いて確認すること。

## 2. 技術構成

## 6. 機能仕様の要点

### 回廊ルーティング（lib/routing.ts）— このプロダクトの心臓部

```
入力: 現在地(スポット or スタート地点), 目的地, 訪問済みID[], 許容寄り道 tolerance_m(既定220)
1. 未訪問スポットを dist(候補→目的地) でスコア化
2. dist(候補→目的地) < dist(現在地→目的地) + tolerance_m のものを回廊プールとする
3. プールが2未満なら、目的地に近い順の上位3件をフォールバックプールとする
4. 重み = (3 - congestion_level) × capacity_weight。時間帯ルール・混雑ルールで重みを乗算補正
   - 食べどき: `meal_times` の帯の中は2.0倍 / 外は0.25倍（飲食スポットのみ）
   - 開いている時間: `open_hours` の外は0.05倍 / 閉店1時間前は0.4倍（全スポット）
   - キャパ重みの決め方は `docs/capacity-guide.md`、時間の扱いは `docs/hours-guide.md`
5. 重み付き抽選で2件返す（choice_shownとしてscansに記録）
```

距離は等距円筒近似でよい（モックアップ `distM()` と同一式）。ルールは `routing_rules` テーブルの
`rule_type`（random/time/congestion/context）+ `config` JSONB で駆動し、コードにマジックナンバーを埋めない。

### QRとセッション

- QRトークン: `qr_token`（spots/campaigns）。URL形式 `/{APP_URL}/s/{qrToken}`
- 匿名セッション: 初回アクセスで `sessions` 行を作成、署名付きcookieにsession_id。**PIIは一切取らない**
- スタンプ: `scans` へINSERT時に一意制約 `(session_id, spot_id)` で二重押印を防ぐ（モックアップの既知バグ対策をDB層で担保）
- レアスタンプ: 判定はサーバー側。`spots.rare_config` JSONB（時間帯・天候・確率）

### ナビ連携

Google マップ ディープリンク `https://www.google.com/maps/dir/?api=1&destination={lat},{lng}&travelmode=walking`。
iOSでGoogle マップ未導入の場合に備え、UA判定でApple マップ `https://maps.apple.com/?daddr={lat},{lng}&dirflg=w` を出し分け。
タップは `scans.nav_clicked` に記録。

**外部デジタルマップへの差し替え**: `MAP_NAV_URL_TEMPLATE`（`src/lib/nav.ts`）を設定すると、
区間ナビの遷移先を MapPenguin 等の観光デジタルマップに置き換えられる。
★**全スポットが載った回遊マップを指定してはいけない。** 次の行き先が一覧で見えた時点で
回廊ルーティングが無意味になる（§9-1と同じ理由）。連携は「1地点だけを開くURL」に限る。

### スポンサーCM

表示位置は**スタンプ獲得演出の直後**（報酬直後が離脱最小）。15秒・スキップ可。
同一セッションへの表示は `cm_frequency_cap`（campaign設定、既定: 3スポットに1回まで）。
表示・完視聴を `cm_impressions` に記録。

### 多言語

ja / en / zh / ko。`Accept-Language` で初期判定、手動切替をセッションに保存。
コンテンツは `spots.name / story / navi_lines` のJSONB多言語カラム（キー = 言語コード）。

### 構造化データ・AEO（seo-aeo §2準拠）

- 参加者ページ: `TouristAttraction` + `BreadcrumbList` のJSON-LD
- サービスサイト側: `Organization` + `FAQPage`。「まわりみちは、目的地までの道中を分散設計する動的QR周遊サービスです」の構文を全ページ統一
- `robots.txt` でAIクローラー（GPTBot / ClaudeBot / PerplexityBot）を許可

## 9. 注意事項・制約 ★最重要

**やってはいけないこと**

1. **目的地への一括ナビを実装しない。** ナビは常に「現在地→次の1スポット」の区間のみ。
   目的地座標をナビリンクに渡すのは最終区間（5個目→ゴール）だけ。全行程ナビを付けると
   参加者がスポットを飛ばして直行し、分散＝プロダクトの存在意義が崩壊する
2. **完全ランダムに戻さない。** 目的地は必ず参加者が選ぶ。回廊制約を外すと「連れ回される」体験に劣化する
3. **PIIを取らない。** 氏名・メール・電話・正確なGPS常時取得は禁止。匿名セッションのみ。
   これは自治体審査を通すための仕様であり、フォームを「便利だから」で追加しない
4. **CMを目的地選択前・スポット閲覧前に挟まない。** スタンプ獲得後のみ
5. モックアップのJSは Vanilla JS。**React移植時、JSX内の日本語全角カッコがBabel系ツールをクラッシュさせた前例あり**。
   文字列リテラル内に収め、JSX直書きの全角記号に注意

**未確定事項とクリティカルパス**

- **QRトークンのURLスキームは、サイネージ・看板の印刷入稿前に確定必須**（過去案件でラベル印刷が
  クリティカルパスになった実例あり。同じ事故を起こさない）
- 実在スポット（六波羅蜜寺ほか8箇所）・d食堂特典は**許諾未取得**。本番データ投入・対外公開前に許諾 or 差し替え
- 「まわりみち」商標はJ-PlatPat確認・出願前。**対外露出（自治体提案・公開デプロイ）の前に出願を済ませる**
- 混雑外部APIは未契約。Phase 1は自社スキャンログ密度のみで congestion_level を手動/半自動更新。
  ただし実証実験の規模（1日11セッション＝密度0.7）では自動連動は発火しない（`docs/capacity-guide.md` §5）
- **飲食スポット5件（喫茶朝霧 / 食堂なゝかまど / 甘味ひとやすみ / 居酒屋みやこ路地 / 町家珈琲みずのわ）は
  実在しない架空の店**。実在の個人店に勝手な割引特典を紐づけないため、最初から架空にしてある。
  参加店が決まったら管理画面から名前・座標・特典を差し替える
- **営業時間（open_hours）は一般に知られている時間を置いただけの仮データ**。季節変動・定休日・最終受付は未反映。
  現地確認が必須。ズレると「開いている前提で送ったら閉まっていた」＝最短ルートより悪い体験になる
- ナビキャラ「ルル」の使用は権利者の許諾が前提。対外公開の前に確認する

## 10. 実装で踏んだ罠（2026-08-03 Phase 1 実装時）

1. **Server Action は multipart/form-data でないと発火しない。**
   `application/x-www-form-urlencoded` でPOSTすると Server Action として扱われず、
   ただのページGETとして200が返る（エラーも出ないので気づきにくい）。
   `origin` ヘッダも必要。E2Eスクリプトは `FormData` で送っている
2. **congestion ルールを既定で入れると受け入れ基準を割る。**
   基本重み `(3 - congestion_level) × capacity_weight` が既に混雑を織り込んでいるため、
   静的な congestion ルールを重ねると同じ信号の二重計上になり、ルートが収束する。
   実測: 清水寺のユニークルートが 433 → 364 に低下（基準は400以上）。
   既定ルールは time（ピーク帯の抑制）+ random（jitter 0.5）のみ。
   congestion ルールは Phase 2 の動的補正用に予約する。設定を変えたら `npm run sim` で実測すること
3. **ユニークルート数は「ルール無し」が上限。** 分散を強めるほどルートの多様性は落ちる。
   清水寺（最も回廊が狭い）はルール無しで433〜455が上限で、基準の400は余裕が小さい。
   ルールを触るときは必ず 20シード以上で最悪値を見る（1シードだと「たまたま通る」）
4. **二択はセッションIDと押印数からシードを決めて再現可能にしている**（`journey.ts`）。
   リロードで二択が変わると体験が壊れるのと、押印時に「何を提示したか」を
   再計算して `scans.choice_shown` に残せなくなるため
5. **`next start` は NODE_ENV=production なので fail-closed ガードが効く。**
   `QR_TOKEN_SECRET` 未設定だとセッション発行で落ちる（設計通り）。ローカル検証時も .env.local が要る
6. 0001_init.sql に無い表示用メタ（`campaigns.start_label` / `goals.grad` / `spots.grad`）を
   0002 で追加している。スキーマを再作成するときは 0002 も流すこと
7. **受け入れ基準（ユニークルート400通り以上）は時間帯を選ばないと成立しない。**
   営業時間を入れた時点で、17時以降は開いているスポットが2〜3件になり、どうやっても基準を割る。
   テストは `OPERATING_HOURS`（9〜16時）で判定し、夜は「二択が返り続けること」だけを担保している。
   ここを全時間帯で通そうとすると、閉まっている場所へ送る設定に戻すしかなくなる
8. **スポットを増やすと、件数を決め打ちしたテストが壊れる。**
   `SPOTS.slice(0, 7)` のような書き方は `SPOTS.length - 1` にする（8→13件で実際に踏んだ）
9. **レアスタンプの時間窓が営業時間の外に出ていないか。** 渉成園のレア窓は 6〜10時だったが
   開園は9時なので、6〜9時は誰も取れない窓だった。テストで機械的に検査している
