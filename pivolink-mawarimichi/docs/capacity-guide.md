# キャパ重みの決め方

管理画面の「キャパ重み」に何を入れるかの基準。2026-08-18 に実測して決めた。

---

## 1. 単位の定義

キャパ重みは抽象値ではなく、**時間あたりの受入人数から決まる**。

混雑の自動連動はこう判定している。

```
密度 = 直近60分のスキャン数 ÷ キャパ重み
密度 3以上 → 0.75倍 ／ 6以上 → 0.45倍 ／ 10以上 → 0.2倍
```

つまり **密度3＝抑制の開始点**。ここから逆算すると:

> **キャパ重み = そのスポットが1時間に無理なく受け入れられる「まわりみち参加者」の数 ÷ 3**

| 1時間に受け入れられる人数 | キャパ重み |
|---|---|
| 3人 | **1.0** |
| 6人 | 2.0 |
| 9人 | 3.0 |
| 1.5人（ごく小さい） | 0.5 |

「無理なく」＝ その場所の体験が損なわれない人数。行列ができる／写真が撮れない／
店主が対応しきれない、が始まる手前。

## 2. 場所の性格からの目安

| 場所の性格 | 同時に居て気持ちよい人数 | キャパ重み |
|---|---|---|
| 路地奥の小さな社、記念館の一室、個人店 | 2〜3人 | **0.5 〜 1.0** |
| 中規模の寺の境内、庭園、カフェ | 5〜10人 | **1.5 〜 2.0** |
| 大きな寺の広い境内、商店街、公園 | 20人以上 | **2.5 〜 3.0** |

**3.0 を超える値は入れなくてよい。** 実測で効果が頭打ちになる（§3）。

## 3. どこまで効くか（実測値）

建仁寺のキャパ重みだけを変えて1,500周まわした結果。

| キャパ重み | 二択に出た率 | ユニークルート | 二択破綻 |
|---|---|---|---|
| 0.5 | 16.4% | 446 | 0 |
| 1.0 | 20.7% | 500 | 0 |
| 2.0 | 25.0% | 532 | 0 |
| 3.0 | 27.4% | 505 | 0 |
| 5.0 | 29.7% | 515 | 0 |
| 8.0 | 32.0% | 495 | 0 |

読み取れること:

- **8倍にしても出現率は2倍弱**。二択という形式上、1回の抽選で選べるのは2件なので上限がある
- **どの値でもルートの多様性は壊れない**（400通り以上・二択破綻0）。安心して動かしてよい
- 実用上は **0.5〜3.0** で十分。それ以上は労力に対して効果が出ない

送客を大きく増やしたいのにキャパ重みが効かない場合、原因は重みではなく**位置**である
ことが多い（回廊から外れていて、そもそも候補に入っていない）。

## 4. キャパ重みが持つ2つの役割

同じ値が2箇所で使われる。方向は一致しているので矛盾しない。

| 役割 | 効き方 |
|---|---|
| 送客量 | 基本重み `(3 − 混雑度) × キャパ重み` を通じて、二択に出る確率を上げる |
| 混雑判定の分母 | 密度 `スキャン数 ÷ キャパ重み` を通じて、混雑と判定されにくくする |

＝ **受け入れられる場所には多く送り、多く来ても混雑扱いしない。**

## 5. ★実証実験の規模では、混雑の自動連動は発火しない

これは正常な状態。理解した上で運用する。

| 1日のセッション数 | 1スポットあたりの密度 | 自動連動 |
|---|---|---|
| 11（実証実験の想定＝3ヶ月1,000件） | 0.7 件/時 | **発火しない** |
| 30 | 1.9 件/時 | 発火しない |
| 60 | 3.8 件/時 | 発火する |
| 120 | 7.5 件/時 | 発火する |
| 300 | 18.8 件/時 | 発火する |

**理由**: 実証実験の規模では、まわりみち参加者だけで物理的な混雑は起きない。
1日11セッション×5スタンプ＝55スキャンを8スポット・10時間で割ると、1スポットあたり0.7件/時。
抑制の開始点（密度3）に遠く届かない。

**だから何をするか**:

1. **実証実験では発火しなくてよい。** 仕組みが入っていることの確認に留める
   （動作検証は `npm test` の混雑連動テストで担保している）
2. **本当に混雑を見たいなら、外部の混雑データが要る。** まわりみち参加者の密度は、
   実際の観光地の混雑とは別物。企画書に書いた「外部混雑データ」がここで効く（Phase 2）
3. 実証実験中に発火の様子を見たい場合は、閾値を一時的に下げる。
   コードではなく `routing_rules.config` を変えるだけで反映される

```json
{ "window_min": 60, "per_capacity": true,
  "thresholds": [
    { "from": 1.5, "multiplier": 0.8 },
    { "from": 3,   "multiplier": 0.55 },
    { "from": 5,   "multiplier": 0.3 }
  ] }
```

変更前に `npm run sim` で効き方を実測すること。

## 6. 迷ったときの初期値

**全スポット 1.0 から始める。** 実証実験のデータが溜まってから、
「提示無視率が低いのに送客が足りない場所」だけ 1.5〜2.0 に上げる。

最初から差をつけると、何が効いたのか分からなくなる。
