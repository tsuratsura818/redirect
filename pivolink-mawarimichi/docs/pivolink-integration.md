# まわりみちは、PivoLinkの機能で動いている

このプロジェクトの目的は「まわりみちというサービスを作ること」だけではない。
**PivoLinkで何ができるかを見せて、活用アイデアと登録ユーザーを増やすこと**が起点にある。

したがって「PivoLinkを使って作った」では足りず、**PivoLinkの機能が実際に動かしている**必要がある。
この文書はその境界を定義し、証明の仕方を書く。

---

## 1. 役割分担

| | 担当 | 何を決めるか |
|---|---|---|
| **PivoLink** | `redirect_rules` | **どのURLへ飛ばすか** — 時間帯・読込回数・ランダム・期間 |
| まわりみちアプリ | Next.js | **そのURLで何を見せるか** — 物語・スタンプ・スタンプ帳・回廊の整合性 |

```
QR（印刷後は不変）
  └→ https://redirect.tsuratsura.com/r/mawarimichi-kenninji
       └→ PivoLink が redirect_rules を評価
            time_of_day  営業時間外か      → ?closed=1
            scan_step    この端末で何回目か → ?visit=2&pick=b
            ab_test      重み付きランダム   → ?pick=a | b | c
       └→ https://mawarimichi.vercel.app/s/dev-kenninji?band=day&pick=b
            └→ アプリは PivoLink の判断に従って画面を出す
```

受け口は [`src/lib/pivolink.ts`](../src/lib/pivolink.ts) の1ファイルだけ。
アプリ側が勝手に時刻を見て分岐しないよう、入口を絞ってある。

## 2. 実際に入れたルール（QR14件・合計97件）

| ルール種別 | 件数 | 使い方 |
|---|---|---|
| `time_of_day` | 27 | スタートQR＝朝/昼/夕の3つ。スポットQR＝**営業時間の「外」だけ**に張って閉店案内へ |
| `scan_step` | 28 | 2回目・3回目の読み込みは別の枝へ（リピート施策） |
| `ab_test` | 42 | 重み34/33/33でa/b/cに振る。**「毎回違う道」の本体** |

`node _create-mawarimichi-rules.mjs --dest <url>` で作成、`--list` で確認、`--delete` で撤去。
すべて **PivoLinkのダッシュボードから手で編集できる形**で入っている。

### ★最初に踏んだ設計ミス

PivoLinkの評価順は
`schedule > scheduled_switch > time_of_day > scan_step > device > ab_test > default`
で、**先に当たったものが勝つ**（[resolver.ts](../../src/lib/redirect/resolver.ts)）。

最初、時間帯ルールで朝/昼/夕と1日を覆ってしまい、**A/Bテストが一度も発火しなかった**。
5回叩いても行き先が `?band=day` のまま同じ。

直し方は「評価順と戦わない」こと。**時間帯ルールを営業時間の外だけに張る**と、
営業時間内は time_of_day に当たらず、下位の scan_step / ab_test まで落ちてくる。

| 状況 | 当たるルール | 行き先 |
|---|---|---|
| 営業時間外 | `time_of_day` | 閉店案内 |
| 営業時間内・2回目以降 | `scan_step` | 前と違う枝 |
| 営業時間内・初回 | `ab_test` | 毎回ランダムな枝 |

これはPivoLinkを使う人が必ず踏む所なので、**ダッシュボードのUIで警告を出す価値がある**
（「時間帯ルールで1日を覆うと、A/Bテストは発火しません」）。企画から出た製品改善の種。

## 3. 「PivoLinkが動かしている」ことの証明

`npm run e2e:pivolink -- https://mawarimichi.vercel.app` で機械的に確認できる。

```
✅ 同じQRから複数の行き先が返る（ab_test） — pick=a / pick=b / pick=c
✅ 居酒屋QR（17-23時）: いま13時 → 閉店中なので閉店案内 — /s/dev-miyakoroji?closed=1
   pick=a  →  市比賣神社 ／ 甘味 ひとやすみ
   pick=b  →  六波羅蜜寺 ／ 食堂 なゝかまど
   pick=c  →  喫茶 朝霧 ／ 渉成園
✅ PivoLink の枝が変わると二択も変わる（＝PivoLinkがルーティングしている） — 3 通り
✅ 二択は出る（自前の時刻判定にフォールバック）
✅ 開示は出ない（PivoLink を経由していないため）
```

**同じQR・同じ時刻・同じ参加者でも、PivoLinkが振った枝で寄り道が変わる。**
これが実演の核。デモでは `--list` でルールを見せてから、QRを3回読ませればいい。

さらに画面上でも開示している。二択の上に出る

> **PivoLink**のルールで選ばれました — 時間帯:昼 / A/B:a

は、PivoLinkのダッシュボードでルールを止めると**実際に消える**。
「裏で動いている」ではなく「止めると変わる」まで示せる状態にしてある。

## 4. アプリ側がPivoLinkに依存しない一線

**「閉まっている場所へ送らない」判定だけは、PivoLinkのパラメータを信じない。**

URLは共有もブックマークもされる。古い `?band=day` を握ったまま夜にアクセスされたら、
閉館後の寺へ人を送ることになる。そこで `open_hours` による安全側の判定は、
アプリが常にサーバー時刻で行う（[`src/lib/hours.ts`](../src/lib/hours.ts)）。

PivoLinkは**体験の分岐**を決める。アプリは**事故を防ぐ**。この線は動かさない。

## 5. 実験期間の開始・終了 — PivoLinkだけで完結する

`_create-mawarimichi-campaign.mjs` で、全QRに2本のルールを張っている。

| ルール | 条件 | 行き先 |
|---|---|---|
| `schedule` | 開始日時より前 | `/notyet`（まだ始まっていません） |
| `scheduled_switch` | 終了日時を過ぎたら | `/finished`（お礼） |

評価順が `schedule > scheduled_switch > time_of_day > ...` なので、
**期間外は必ずこの2本が勝ち、期間中はどちらも当たらず通常のルールに落ちる。**

意味するところは運用コストで、**現地の看板・サイネージ・チラシを一度も触らずに、
開始日に体験がひらき、終了日に閉じる。** 回収に行く必要がない。

実際に終了日時を過去に倒して確認した:

```
終了日を過去に倒したとき → https://mawarimichi.vercel.app/finished
元に戻したとき           → https://mawarimichi.vercel.app/s/dev-rokuhara?pick=b
```

日時は `--start` / `--end`（JST）で入れ替えられる。JST→ISO変換を挟んでいるので9時間ズレない。

## 6. スポンサーCM — クッションページがそのまま広告枠

```
スタンプ3個ごと（アプリが判断）
  → /r/mawarimichi-cm          入口。ab_test でスポンサーを50/50に振る
    → /r/mawarimichi-cm-a|b    クッションページ＝広告クリエイティブ本体
      → /cm/return             アプリが元の画面へ戻す
```

広告の**文言・背景色・ロゴ・表示秒数・クーポンコード・注記**はすべて `cushion_pages` に入り、
**PivoLinkのダッシュボードから編集できる**。アプリ側に広告の実装は一行も無い。

| | 担当 |
|---|---|
| いつ挟むか（3個ごと・1個目は出さない） | アプリ（参加者ごとの状態なので） |
| 何を見せるか・何秒・スキップ・クーポン | **PivoLink のクッションページ** |
| どのスポンサーを見せるか | **PivoLink の ab_test** |
| 表示回数の計測 | **PivoLink の scan_logs / アナリティクス** |

★表示回数がPivoLink側に乗るので、まわりみちに `cm_impressions` を持つ必要がなくなった。
★`MAWARIMICHI_CM_URL` 未設定ならCMは出ない（fail-safe）。env を外せば広告だけ止められる。
★CMは**スタンプ獲得の直後だけ**（CLAUDE.md §9-4）。目的地選択前・スポット閲覧前には絶対に挟まない。
　PivoLinkのクッションは本来「着地の手前」に出る機能だが、スポットQRに付けると
　この原則を破るので、**スポットQRにはクッションを付けていない**。CM専用QRを別に立てている。

## 7. 第三者に渡せる状態（スクリプト不要）

**PivoLink とまわりみちを渡せば、スクリプトを一度も叩かずに運用を始められる。**

| 操作 | 画面 | PivoLink側に何が起きるか |
|---|---|---|
| セットアップ確認・初回SQL | `/admin/setup` | — |
| キャンペーン設定・開催期間 | `/admin/campaign` | `schedule` / `scheduled_switch` を全QRに張り直す |
| スタートQRの登録 | `/admin/campaign` | QR + `time_of_day`×2 + `scan_step`×2 + `ab_test`×3 |
| スポンサーCM枠 | `/admin/campaign` | CM枠QR + クッションページ + 入口の `ab_test` |
| 目的地の追加・編集 | `/admin/goals` | （QRは作らない。目的地は読ませる場所ではない） |
| スポットの追加・編集 | `/admin/spots/*` | QR + 営業時間から `time_of_day` + `ab_test`×3 |
| 見出し・ナビの名前と台詞・画像・朱印・OG画像 | `/admin/campaign` | — （まわりみち側の表示だけ） |
| ルールの微調整・アナリティクス | PivoLink のダッシュボード | — |

`_create-mawarimichi-*.mjs` は**復旧用のフォールバック**として残しているだけで、
運用手順には載せない。載せた時点で第三者に渡せなくなる。

★**QR画像は必ず PivoLink の `/r/` を焼く。** アプリの直URLを刷ると全機能が素通りになり、
しかも後から遷移先を変えられない。管理画面のQR発行はこれを自動で判定している。

## 8. まだPivoLinkに寄せていないもの

| | 現状 | 寄せられるか |
|---|---|---|
| 回廊の絞り込み（目的地に近づく候補だけ） | アプリ | ✕ 訪問済みリストと目的地という参加者ごとの状態が要る。ステートレスなリダイレクトでは原理的に無理 |
| スタンプ・スタンプ帳 | アプリ | ✕ 同上 |
| 混雑の自動連動 | アプリ | △ スキャンログはPivoLink側にもあるので将来的には寄せられる |

**この3つがまわりみちのオリジナル機能。** 逆に言えば、
「毎回行き先が変わる」「時間で変わる」「回数で変わる」「期間で切り替わる」「広告を挟む」は
**すべてPivoLinkの標準機能**で、コードを書かずにダッシュボードから設定できる。
